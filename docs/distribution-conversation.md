# CodexPet 전역 설치와 배포 준비 대화

작성일: 2026-11-05  
목적: 학교 컴퓨터에서 나눈 대화를 집에서도 확인할 수 있도록 질문과 답변을 정리한다.

이 문서는 대화 내용을 주제별로 충실히 옮긴 기록이다. 설치나 배포 작업을 수행했다는 뜻은 아니다. 명령과 설정 예시는 사용 전에 실제 환경과 현재 문서를 확인해야 한다.

## 1. 내 컴퓨터에 전역적으로 설치하기

### 질문

> 이 프로젝트를 내 컴퓨터에 전역적으로 설치해서 모든 Codex 작업 또는 워크모드 작업에 반응할 수 있게하려면 어떻게 해야하는지 설명만 해줘. 파일은 수정하거나 새로 생성하지 마.

### 답변

Windows에서 위젯을 계속 실행하고, 사용자 전역 Codex 훅이 이벤트를 위젯에 전달하도록 설정하면 여러 프로젝트에서 사용할 수 있다. 다만 모든 Codex·Work 작업을 빠짐없이 감지하는 것은 현재 구조만으로 보장되지 않는다. 특히 클라우드에서 조정하는 작업에는 로컬 명령 훅이 적용되지 않는다.

#### 앱과 훅 실행 파일 배포

이 프로젝트에는 화면을 보여주는 `CodexPet.App`과 이벤트를 전달하는 `CodexPet.Hook`이 따로 있다. 프로젝트는 .NET 10을 대상으로 하므로 빌드하는 컴퓨터에는 .NET 10 SDK가 필요하다.

예를 들어 프로젝트 폴더에서 PowerShell로 다음을 실행해 각각 고정된 위치에 게시할 수 있다.

```powershell
dotnet publish .\CodexPet.App\CodexPet.App.csproj -c Release -r win-x64 --self-contained true -o "$env:LOCALAPPDATA\CodexPet\App"

dotnet publish .\CodexPet.Hook\CodexPet.Hook.csproj -c Release -r win-x64 --self-contained true -o "$env:LOCALAPPDATA\CodexPet\Hook"
```

이 예시는 64비트 Windows용이며 게시 결과에 .NET 런타임을 포함한다. 두 폴더의 전체 게시 결과를 유지해야 한다. 업데이트할 때도 같은 위치에 다시 게시하면 전역 훅의 경로를 유지할 수 있다.

#### 위젯 실행 및 자동 시작

게시 후 다음 파일을 실행하면 위젯이 켜지고 이벤트를 받을 준비를 한다.

```text
%LOCALAPPDATA%\CodexPet\App\CodexPet.App.exe
```

Windows 로그인 때마다 자동으로 켜려면 `Win + R` → `shell:startup`으로 시작프로그램 폴더를 열어 실행 파일의 바로 가기를 넣으면 된다. 위젯이 꺼져 있을 때 이벤트 전달에 실패하더라도 Codex 작업은 계속된다. 위젯을 나중에 켰을 때 이전 작업 상태는 복구하지 않는다.

#### 사용자 전역 훅 등록

현재 프로젝트의 [`.codex/hooks.json`](../.codex/hooks.json)은 프로젝트별 설정이고, 훅 실행 파일도 프로젝트 내 상대 경로를 가리킨다. 다른 프로젝트에서도 사용하려면 사용자 홈의 다음 위치에 훅을 등록하고 실행 파일을 절대 경로로 지정해야 한다.

```text
C:\Users\SSAFY\.codex\hooks.json
```

예를 들어 `UserPromptSubmit` 이벤트 하나의 설정은 다음 형태다. `command` 안의 역슬래시는 JSON 문법에 맞춰 두 개씩 쓴다.

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "& \"C:\\Users\\SSAFY\\AppData\\Local\\CodexPet\\Hook\\CodexPet.Hook.exe\"",
            "timeout": 2
          }
        ]
      }
    ]
  }
}
```

이 예시 하나만 등록하면 요청 제출에만 반응한다. 현재 위젯의 상태 전환에 필요한 다음 이벤트에도 같은 실행 파일을 등록해야 한다.

- `SessionStart`, `SessionEnd`, `Interrupt`, `Stop`
- `UserPromptSubmit`
- `PreModelRequest`, `PostModelRequest`
- `PreToolUse`, `PostToolUse`, `PermissionRequest`

기존 프로젝트 설정을 바탕으로 각 `command`를 절대 경로로 바꾸는 방법이 있다. 이미 사용자 전역 `hooks.json`이나 `config.toml`에 훅이 있다면 덮어쓰지 말고 기존 설정과 합쳐야 한다.

전역 훅과 프로젝트 훅은 함께 실행된다. 이 프로젝트에서 이벤트가 두 번 전달되지 않도록 전역 등록 후에는 기존 프로젝트 훅 설정을 정리하는 편이 좋다. 새로 추가하거나 변경한 비관리 훅은 검토와 신뢰가 필요하며, CLI의 `/hooks`에서 확인할 수 있다. [OpenAI 훅 문서](https://learn.chatgpt.com/docs/hooks)

#### 적용 범위와 한계

- **로컬 Codex 작업:** 같은 Windows 사용자 계정에서 로컬로 실행되고 해당 전역 훅을 읽는 작업이라면 다른 프로젝트와 로컬 worktree에서도 반응하도록 구성할 수 있다. 실제 환경별 테스트가 필요하다.
- **로컬 전용 Work 작업:** 작업 조정과 실행이 모두 로컬인 경우 지원되는 훅을 사용할 수 있다고 공식 문서에 나와 있다. 계정과 앱 환경에서 실제 이벤트가 전달되는지는 확인해야 한다.
- **Codex Cloud 및 클라우드로 조정되는 Work:** 내 PC의 훅 실행 파일과 Windows named pipe가 클라우드 작업에 자동으로 연결되지는 않는다. Work Cloud에서는 로컬 설정의 명령 훅이 지원되지 않으며, 지원되는 경우 관리자 정의 원격 MCP 훅을 사용한다. 이를 이 위젯에 연결하려면 별도의 중계 설계와 구현이 필요하다. [OpenAI 훅 문서](https://learn.chatgpt.com/docs/hooks), [Codex 실행 환경](https://learn.chatgpt.com/docs/environments/modes)
- **여러 작업 동시 실행:** 현재 코드는 세션별 상태를 집계하지 않고 마지막으로 도착한 이벤트를 표시한다. 한 작업이 끝나면 다른 작업이 진행 중이어도 위젯이 대기 상태로 바뀔 수 있다. [상태 표시 명세](features/show-state-widget.md)
- **실행 환경:** 예시는 Windows에서 훅 명령을 실행하는 경우다. WSL이나 원격 컴퓨터에서 실행되는 Codex는 Windows 실행 파일 경로와 named pipe 접근 방식이 달라 별도 확인이 필요하다.

설정 후 위젯을 켠 상태로 다른 로컬 프로젝트에서 새 Codex 작업을 시작해 상태가 바뀌는지 확인한다. 전달이 안 되면 `%LOCALAPPDATA%\CodexPet\Logs`의 `hook.log`와 `app.log`, `/hooks`의 신뢰 상태, 실행 파일 경로를 확인할 수 있다.

당시에는 설명만 했으며 설치나 실제 연동 시험은 수행하지 않았다.

## 2. 친구들에게 배포하기

### 질문

> 그런데 친구들한테도 이걸 주려면 어떻게 배포할 지 잘 모르겠어.

### 답변

친구들에게는 설치 파일 하나를 실행하면 위젯과 Codex 훅이 함께 설정되는 방식이 편하다. 이 프로젝트라면 Windows용 설치 파일 `CodexPet-Setup.exe`를 만들고 GitHub Releases 같은 곳에 올려 배포하는 방식을 추천했다.

친구 입장에서는 다음 정도로 끝나게 만드는 것이 목표다.

1. 설치 파일을 다운로드해서 실행한다.
2. 설치 화면에서 Windows 시작 시 자동 실행 여부를 선택한다.
3. Codex에서 새 훅 내용을 검토하고 신뢰한다.
4. 위젯을 실행한 뒤 로컬 Codex 작업을 시작한다.

훅 신뢰는 설치 프로그램이 대신 건너뛰기보다 친구가 직접 확인하도록 안내한다. Codex 데스크톱 앱의 **Settings → Hooks** 또는 CLI의 `/hooks`에서 검토할 수 있다. [OpenAI 훅 문서](https://learn.chatgpt.com/docs/hooks)

#### 설치 파일에 들어갈 것

- **CodexPet.App:** 화면에 펫을 표시하는 Windows 앱
- **CodexPet.Hook:** Codex의 이벤트를 앱에 전달하는 프로그램

두 프로그램을 self-contained 방식으로 게시하면 필요한 .NET 런타임이 포함되므로 친구가 .NET SDK나 런타임을 따로 설치하지 않아도 된다. 대신 설치 파일의 용량은 커진다. 일반적인 64비트 Windows용 `win-x64`부터 제공하고 ARM Windows 지원이 필요해지면 별도 빌드를 추가할 수 있다. [Microsoft .NET 배포 문서](https://learn.microsoft.com/en-us/dotnet/articles/core/deploying/)

설치 프로그램 제작 도구로는 Windows 설치 마법사와 시작 메뉴 바로 가기 등을 만들 수 있는 [Inno Setup](https://jrsoftware.org/isinfo.php)을 제안했다.

#### 설치 프로그램이 해야 할 일

- 친구의 사용자 폴더 아래에 앱과 훅을 설치한다.
- 친구의 `~/.codex/hooks.json`에 CodexPet 훅을 등록한다. 훅 실행 파일 경로는 친구 컴퓨터의 설치 경로를 사용한다.
- 기존 훅 설정이 있으면 보존하면서 CodexPet 항목을 추가한다.
- 자동 시작은 선택 사항으로 제공하고 선택한 경우 시작프로그램 바로 가기를 만든다.
- 삭제할 때는 CodexPet이 추가한 훅과 바로 가기만 제거한다.

훅 설정 병합과 삭제는 새로 만들어야 하는 부분이다. 현재 저장소의 훅 설정은 프로젝트 개발용 상대 경로를 사용하므로 그대로 친구에게 전달할 수 없다. 훅 정의가 변경되면 다시 신뢰해야 할 수도 있다. [OpenAI 훅 문서](https://learn.chatgpt.com/docs/hooks)

#### 배포 전에 준비할 것

당시 확인한 범위에서 프로젝트에는 앱과 훅 구현은 있지만 설치 프로그램, 전역 훅 등록 및 제거 기능, 배포 자동화는 없었다. 설치·삭제 흐름을 구현하고 개발 환경이 없는 Windows 계정이나 PC에서 다음을 확인하는 것이 좋다.

- 설치 후 다른 프로젝트의 로컬 Codex 작업에 반응하는지
- 기존 Codex 훅이 유지되는지
- 업데이트와 삭제 후에도 기존 설정이 유지되는지
- 위젯을 종료해도 Codex 작업이 정상 진행되는지
- 동시에 여러 작업을 할 때 표시가 기대와 일치하는지

현재 코드는 여러 작업의 상태를 따로 추적하지 않아 한 작업에서 도착한 이벤트가 다른 작업의 표시를 덮어쓸 수 있다.

첫 배포 안내에는 Windows 로컬 Codex를 지원 대상으로 명시하는 것이 정확하다. 로컬 전용 Work는 환경별 검증이 필요하고 클라우드로 조정되는 Work는 이 로컬 명령 훅을 그대로 사용할 수 없다. [OpenAI 훅 문서](https://learn.chatgpt.com/docs/hooks)

Codex 플러그인 형태로 훅을 배포하는 방법도 있다. 다만 이것만으로 Windows 위젯의 설치와 실행이 자동으로 해결되는 것은 아니어서 첫 버전은 설치 프로그램부터 만드는 방식을 제안했다. [OpenAI 플러그인 문서](https://learn.chatgpt.com/docs/plugins)

## 3. 친구마다 다른 Windows 사용자 이름

### 질문

> 친구 컴퓨터의 user 이름도 다를텐데, hooks.json에 들은 절대 경로는 어떻게 매번 다르게 만들어?

### 답변

설치 프로그램이 설치되는 컴퓨터에서 사용자 폴더와 설치 경로를 알아낸 뒤, 그 경로를 넣어 `hooks.json`을 만들거나 기존 설정에 추가하면 된다. 배포 파일 안에 사용자 이름을 미리 적어 둘 필요는 없다.

사용자별 앱 폴더로 설치하면 다음처럼 달라진다.

```text
내 컴퓨터:   C:\Users\SSAFY\AppData\Local\CodexPet\Hook\CodexPet.Hook.exe
친구 컴퓨터: C:\Users\친구이름\AppData\Local\CodexPet\Hook\CodexPet.Hook.exe
```

설치 프로그램은 Windows의 사용자별 경로인 `%LOCALAPPDATA%`를 통해 설치 위치를 찾고, Codex 설정 폴더도 해당 사용자의 홈 폴더를 기준으로 찾는다. 그다음 실제로 결정된 설치 경로를 사용해 훅 설정을 쓴다.

예를 들어 친구의 Windows 사용자 이름이 `Minji`라면 설치 후 훅 설정의 해당 부분은 다음처럼 된다.

```json
{
  "type": "command",
  "command": "& \"C:\\Users\\Minji\\AppData\\Local\\CodexPet\\Hook\\CodexPet.Hook.exe\"",
  "timeout": 2
}
```

`\\`는 경로에 역슬래시가 두 개 들어 있다는 뜻이 아니라 JSON 파일에 역슬래시를 표현하는 방식이다. 설치 프로그램이 JSON을 생성할 때 이 변환까지 처리해야 한다.

`hooks.json` 전체를 새 내용으로 덮어쓰지 않는 것이 중요하다. 친구가 이미 다른 훅을 사용하고 있을 수 있으므로 기존 설정을 읽어 CodexPet 항목만 추가하고, 삭제할 때도 그 항목만 제거하도록 만들어야 한다.

## 4. 0.1.0 배포 준비를 Spec으로 나누기

### 질문

> 첫 버젼인 0.1.0 버젼을 내세우기 전에 배포 환경을 만들어야하고, 배포 하기 전에 보안문제가 있는지도 체크해야 될 것 같아. 이 작업들을 Spec 단위로 만드려면 어떻게 쪼개고, 각 Spec에는 어떤 내용을 담아야 할 지 설명해 줘.

### 답변

**배포 기반, 설치·연동, 보안 점검, 릴리스 검증**을 각각의 Spec으로 나누는 것을 추천했다. 각 Spec은 독립적으로 완료 여부를 판단할 수 있어야 하며, 보안 점검 결과에 따라 설치 구현을 고칠 수 있도록 최종 배포 전에 여유를 둔다.

```text
배포 방식 결정
    ↓
빌드·패키징 ──→ 설치·전역 훅 연동
    └────────→ 보안 점검 및 발견 사항 수정
                     ↓
              0.1.0 릴리스 검증
```

보안은 마지막에 한 번만 확인하기보다 설치·훅 연동의 설계를 검토하면서 시작하고 구현 후 다시 검증한다.

### Spec 1. Windows 배포 패키지와 빌드

**목표:** 개발 환경이 없는 친구도 실행할 수 있는 0.1.0 배포물을 재현 가능한 절차로 만든다.

담을 내용:

- 지원 환경: 우선 Windows x64와 로컬 Codex를 대상으로 할지 확정
- `CodexPet.App`과 `CodexPet.Hook`을 Release·self-contained 방식으로 게시
- 두 게시 결과를 설치 프로그램에 포함하는 방법
- 버전 번호 `0.1.0`을 제품 정보와 설치 파일 이름에 반영하는 방법
- 설치 파일 생성 방법과 결과물의 이름·저장 위치
- GitHub Releases 등 배포 채널과 릴리스 노트에 담을 내용
- ARM Windows, 자동 업데이트 등 첫 버전에서 다루지 않을 항목

**완료 기준 예시:** 문서화된 절차로 `CodexPet-Setup-0.1.0-win-x64.exe`를 만들 수 있고, .NET 개발 도구가 없는 테스트 환경에서 설치 및 실행할 수 있다.

이 Spec은 설치 파일을 만들고 전달하는 방법에 집중한다. 실제 전역 훅 병합과 삭제 동작은 다음 Spec에서 정의한다.

### Spec 2. 설치·삭제와 전역 훅 연동

**목표:** 친구가 자신의 Windows 계정에서 설치하면 다른 로컬 Codex 프로젝트에서도 펫이 이벤트를 받을 수 있게 한다.

담을 내용:

- 사용자별 설치 위치와 설치 경로 변경 허용 여부
- 설치 시 실제 경로를 이용해 `~/.codex/hooks.json`에 훅을 등록하는 방식
- 기존 훅 설정을 유지하면서 CodexPet 항목만 추가·제거하는 규칙
- 훅 설정 파일이 없거나 기존 JSON을 읽을 수 없는 경우 사용자에게 보여줄 안내
- 재설치·업데이트 시 동일 훅이 중복 등록되지 않도록 하는 동작
- Windows 로그인 시 자동 실행 옵션의 기본값과 바로 가기 생성·제거
- 설치 후 Codex의 훅 검토·신뢰 방법 안내
- 삭제할 때 앱 설정과 진단 로그를 남길지, 사용자가 선택할지
- 위젯이 꺼져 있을 때도 Codex 작업이 계속되는 기존 동작 유지
- 설치 경로와 전역 훅 등록·제거에 Spec 3에서 정한 보안 요구사항을 반영하고, 기존 사용자 설정을 보존하는지 확인

**완료 기준 예시:** 기존 훅이 있는 계정과 없는 계정에서 각각 설치할 수 있고, 다른 로컬 프로젝트의 Codex 이벤트를 수신한다. 삭제 후에는 기존 훅이 유지되고 CodexPet이 등록한 항목만 제거된다.

여러 Windows 사용자 계정에 대한 설치 범위도 명시한다. 첫 버전은 설치한 사용자 한 명에게만 적용하는 방식이 단순하다.

### Spec 3. 0.1.0 보안 점검 및 개선

**목표:** 친구에게 배포하기 전 현재 코드와 설치 과정에서 실제로 발생할 수 있는 문제를 점검하고 배포에 필요한 수정 사항을 해결한다.

담을 내용:

- **검토 범위:** 앱, 훅 실행 파일, named pipe 통신, 설정·로그 파일, 설치 및 삭제 과정, 배포물
- **데이터 흐름:** Codex 이벤트가 훅에서 앱으로 어떻게 전달되는지, 디스크에는 어떤 정보가 기록되는지
- **이벤트 전송 최소화:** 원본 JSON 전체 대신 위젯에 필요한 필드만 파이프로 전달하도록 개선한다. 현재 상태 표시에 필요한 필드는 `hook_event_name`과 `SessionStart`의 `source`다. 진단 로그에 사용하는 `session_id`의 유지 여부와 상태에 영향을 주지 않는 이벤트의 진단 기록은 별도로 결정한다.
- **설치 설정:** 기존 훅을 손상시키거나 잘못된 실행 파일을 등록할 가능성
- **프로세스 간 통신:** 현재 `CurrentUserOnly` 제한과 그 범위를 확인한다. 같은 사용자 계정의 다른 프로세스가 이벤트를 위조하거나 가짜 서버를 만드는 조건, 입력 크기 및 수신 중단 가능성을 점검하고 배포에 필요한 대응을 정한다.
- **로그와 사용자 데이터:** 이벤트 이름·세션 ID 등 실제 저장 항목, 보관 위치, 삭제 방법을 확인하고 기록 정책을 정한다. 프롬프트 전문이 저장되는지 여부도 코드 기준으로 점검한다.
- **의존성 및 배포물:** 외부 패키지의 알려진 취약점 점검, 배포 파일 출처와 무결성을 사용자가 확인할 방법
- **검증:** `prompt`, `tool_input`, `tool_response` 등 선택하지 않은 필드가 파이프로 전달되지 않으면서 기존 상태 전환이 유지되는지 확인한다. 설치·전역 훅 연동에도 정한 보안 요구사항이 적용되는지 확인한다.
- **결과 기록:** 발견 사항, 재현 조건, 영향, 수정 여부, 데이터 최소화 후에도 남는 파이프 상대방 신원 문제 등 제한 사항을 기록한다.

[훅 입력 정보 필요도](references/hook-input-priorities.md)를 필드 선정의 근거 자료로 사용하고, 최종 전송 필드와 로그 정책은 이 Spec에서 확정한다. 전송 최소화는 훅의 표준 입력 자체를 줄이거나 파이프 상대방의 신원을 검증하지는 않는다.

도구 사용 시 이미지 위 문구에 도구 이름을 표시하는 아이디어는 화면 기능이다. 구현하기로 하면 [위젯 상태 표시 명세](features/show-state-widget.md) 또는 별도 기능 Spec에서 표시 규칙과 0.1.0 포함 여부를 정한다. 해당 기능에 `tool_name`이 필요하다고 결정되면 이 Spec의 전송 허용 필드에도 반영한다.

**완료 기준 예시:** 점검 결과가 기록되어 있고, 배포를 막는 것으로 판단한 문제는 수정 및 재검증된다. 남겨 둔 문제는 영향과 이유가 릴리스 판단에 반영된다.

서명되지 않은 Windows 설치 파일은 경고가 표시될 수 있으므로 코드 서명 인증서를 이번 버전에 도입할지도 결정한다. 서명을 하지 않는다면 배포 페이지에 파일 출처와 해시 확인 방법을 안내하는 방향을 검토할 수 있다.

### Spec 4. 0.1.0 릴리스 검증과 배포

**목표:** 완성된 설치 파일이 약속한 환경에서 동작하는지 확인하고, 친구가 설치·사용·삭제할 수 있도록 릴리스를 준비한다.

담을 내용:

- 테스트 환경: 개발 도구가 없는 Windows x64 환경, 기존 Codex 설정이 있는 경우와 없는 경우
- 설치 → 훅 신뢰 → 다른 프로젝트에서 작업 → 위젯 반응 → 삭제까지의 전체 시나리오
- 재설치와 업데이트, 위젯이 꺼진 상태의 Codex 작업 확인
- 실제 배포할 설치 파일에서 Spec 3의 보안 요구사항과 검증 결과를 확인하고 남은 제한 사항을 릴리스 판단에 반영
- 지원 범위와 알려진 한계: 로컬 작업 중심, 클라우드 작업 미지원, 여러 세션의 표시가 서로 덮일 수 있음
- 다운로드 위치, 설치·삭제 안내, 문제 발생 시 로그 위치와 문의 방법
- 버전 번호, 변경 사항, 배포 파일 및 해시 확인
- 릴리스 승인 기준: 앞선 Spec의 완료 상태와 보안 점검 결과 확인

**완료 기준 예시:** 실제 배포할 설치 파일로 전체 시나리오를 통과하고, 설치 안내와 알려진 제한 사항을 포함한 0.1.0 릴리스 초안이 준비된다.
