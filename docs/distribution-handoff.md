# 0.1.0 배포 준비 작업 인계

작성일: 2026-11-10

대상: Windows 11 x64의 로컬 Codex를 사용하는 CodexPet 0.1.0

최신 상태: 트레이 기능과 라이선스 확인 화면을 포함한 새 설치 파일을 빌드하고, 별도 시험용 설치 파일로 무인 설치 동의 인자·설치·제거·고지를 격리 검사했다. 새 파일의 실제 설치·화면 검증과 Microsoft 조건·사용자 약관 검토, 공개 승인은 남았다. 이전 Sandbox 결과는 이전 후보에만 해당한다. 새 파일 식별값과 검토 항목은 [라이선스 검토](features/distribution-license-review.md#사용자-진행-요청-후-설치-화면-반영--2026-11-10)를 따른다.

이후 사용자가 실제 화면과 라이선스 확인 항목을 확인했다고 보고했다. 시험 환경·파일 해시·세부 근거는 제공되지 않았으며 푸시와 공개를 승인한 것은 아니다.

현재 구현과 검증 결과를 바탕으로 다른 PC에서 이어서 할 일을 정리한다. 시험용 설치 파일이 만들어졌다는 사실은 최종 배포 검증이나 공개 승인을 뜻하지 않는다. 각 작업의 실제 결과는 해당 명세와 점검 기록에 반영한다.

## 먼저: 현재 작업을 다른 PC로 옮기기

최초 작성 시점의 브랜치는 `main`, 마지막 커밋은 `a4d72f4`였으며 그 이후 Spec 2·3 구현과 문서가 작업 트리에 있었다. 현재 커밋 및 공유 상태는 바뀌었을 수 있으므로 옮기기 직전에 확인한다. `a4d72f4`만 받으면 그 이후 작업이 빠진다.

- `git log -1 --oneline`과 `git status --short`로 현재 커밋과 수정·삭제·미추적 파일을 확인한다. 필요한 커밋이 다른 PC에서 접근 가능한지 확인하고, 남은 작업 트리 변경이 있다면 검토 후 함께 옮긴다. `git diff`만으로는 미추적 파일을 옮길 수 없다.
- 사용자가 `.codex/hooks.json`을 `.codex/hooks.json.bak`으로 이름 바꾸어 개발용 훅을 비활성화했다. 이 변경을 포함해 인계하고, 다른 PC에서 훅을 임의로 복원하거나 등록하지 않는다.
- Spec 2·3 작업에는 `CodexPet.Install/`, `installer/`, `CodexPet.Tests/InstallationChecks.cs`와 관련 문서가 포함된다. 이 파일들이 다른 PC에 모두 있는지 확인한다.
- `artifacts/`는 Git 제외 대상이므로 시험용 설치 파일, publish 결과와 포터블 Inno Setup은 일반적인 Git 동기화로 옮겨지지 않는다. 다른 PC에서 다시 빌드할 수 있다. `assets/`의 개인 이미지도 Git 제외 대상이다. 현재 이 PC에는 GIF 5개가 있으며, 다른 PC에서도 필요하면 이용 조건을 확인한 뒤 별도로 옮긴다.
- `%LOCALAPPDATA%\CodexPet`의 설정·이미지·로그와 개인 Codex 설정·인증 정보는 소스 이전과 별개다. 필요한지와 내용을 확인해 다룬다. 설치·삭제 검사는 실제 사용자 데이터와 다른 프로그램의 훅을 건드리지 않는 격리 환경에서 수행한다.

### Spec 1에서 할 일

- [x] 앱·훅·설치 보조 프로그램과 설치 파일의 버전을 `version.txt`에서 관리한다.
- [x] [빌드 안내](features/distribution-build-guide.md)에 도구, 복원·빌드·실패 복구와 결과 위치를 기록했다. 현재 시험에는 SDK `10.0.403`, Inno Setup `7.1.1`을 사용했다.
- [ ] CodexPet 자체 MIT 라이선스와 외부 고지를 포함하도록 준비했다. 최종 배포물의 실제 구성과 .NET 런타임의 배포 조건을 공개 전에 재확인한다.
- [ ] 최종 설치 파일에 필요한 실행 파일과 런타임이 있고 개인 이미지나 불필요한 파일이 없는지 확인한다. 개발 도구와 별도 런타임이 없는 지원 환경에서 실행을 검증한다.
- [ ] 최종 파일명·보관 위치, 공개 GitHub Releases 접근성, 지원 범위·변경 사항·제한·설치 안내·미서명 및 Windows 경고·SHA-256 안내를 준비한다. 최종 파일이 확정된 뒤 그 파일의 해시를 계산한다.

### Spec 2에서 할 일

- [ ] 실제 사용자 흐름으로 설치 → Codex에서 훅 검토·신뢰 → 다른 로컬 프로젝트에서 이벤트 수신 → 위젯이 꺼진 상태에서 작업 → 제거를 검증한다. 실제 Codex 버전, 명령 셸과 화면의 동작을 확인한다.
- [ ] `hooks.json`, `config.toml`과 다른 프로그램의 훅이 있는 경우와 없는 경우, 잘못된 설정, 권한 부족, 복구와 재시도, 재설치·업데이트, 위젯 실행 중 설치·제거를 확인한다. 다른 Windows 계정의 설정이 바뀌지 않는지도 검증한다.
- [ ] 제거 화면에서 설정·이미지 사본, 새 로그, 이전 로그의 보존과 개별 삭제를 직접 선택해 확인한다. 자동 시험은 삭제 선택을 **모의**했으므로 실제 화면 조작을 검증한 것은 아니다. 원본 이미지와 다른 프로그램 파일은 보존한다.
- [ ] 공백·한글·특수 문자가 있는 경로를 실제 Codex 실행 경로에서도 확인한다. 격리 시험과 PowerShell 인용 시험만으로 모든 Codex 환경의 동작을 보장할 수 없다.
- [ ] 발견한 문제를 수정하고 [Spec 2](features/installation-and-global-hooks.md)의 완료 기준에 환경·증거·미검증 항목을 기록한다. [설치·복구 안내](features/installation-guide.md)도 실제 동작과 맞춘다.

### Spec 3에서 할 일

- [x] [보안 점검 결과](features/security-review-results.md)에 같은 Windows 계정의 가짜 이벤트와 서버 선점 위험, 근거와 0.1.0 수용 결정을 기록하고 릴리스 안내 초안에 제한을 추가했다.
- [ ] 다른 사용자와 권한·무결성 수준의 파이프 접근, 연속 점유와 입력 제한의 영향을 지원 Windows 환경에서 검사한다. 정상 Codex 이벤트의 실제 크기를 살펴 현행 훅 입력 제한인 1 MiB·1초 등의 적절성을 판단한다.
- [ ] 설정·이미지·로그, 설치와 훅 등록·삭제의 ACL·권한 오류·복구, 실행 파일 및 설정 변조의 영향을 합성 데이터를 사용하는 격리 환경에서 확인한다. 발견한 문제는 수정 후 재검증한다.
- [ ] 2026-11-09의 NuGet 점검을 최신 결과로 간주하지 말고, 최종 빌드의 의존성·포함 런타임·설치 도구·실제 설치 파일을 다시 점검한다. 미서명 사실, SHA-256 비교 방법과 남은 제한을 기록한다.
- [ ] 영향·심각도·재현 조건·수정과 미해결 이유를 남긴다. 릴리스를 막는 문제는 수정·재검증하고, 나머지는 담당자가 판단할 수 있도록 Spec 4에 전달한다.

### Spec 4에서 할 일

- [x] Spec 1~3의 결과와 [질문지](features/release-validation-and-distribution-questions.md) 답변을 [명세](features/release-validation-and-distribution.md)에 반영했다.
- [ ] 대상 환경과 시험 데이터, 설치부터 제거까지의 절차, 기존 훅·여러 세션·오류 복구, 실제 화면·GIF 재생 및 합격 기준을 정한다.
- [ ] 배포하려는 **동일한 최종 설치 파일**로 Spec 1~3 결과를 포함한 최종 검사를 수행한다. 공개 페이지의 파일명·SHA-256·미서명 사실·다운로드 출처·설치법·제한·변경 사항을 준비한다.
- [ ] 공개 판단자와 기준을 명확히 하고 차단 문제와 미해결 사항을 확인한 뒤 릴리스를 결정한다. 이 인계 문서 작성에는 공개가 포함되지 않는다.

## 구현된 명세 중 다시 방문할 것

- [사용자 이미지 명세](features/user-provided-images.md): 이미지 사본 저장, 이미지 없는 상태와 이전 `asset:` 설정 이행 등은 구현과 자동 시험이 있지만, 문서의 ‘구현 전’ 표시와 과거 코드 설명은 오래됐다. 실제 코드·검사와 대조해 상태를 갱신하고 완료와 미검증을 구분한다. 최종 설치 파일에서 이전 GIF가 제외됐는지, 등록한 이미지가 실제로 표시·재생되는지도 확인한다. 과거 Git 이력의 이미지에 대해서는 권리와 공개 상태를 확인한 뒤 대응을 별도로 판단한다.
- [위젯 상태 표시](features/show-state-widget.md): 상태 전환과 파이프 자동 검사는 있지만, 실제 Codex에서 이벤트 순서·승인·중단·압축, `Stop` 등의 빈 표준 출력, GIF 재생과 화면 모양은 아직 확인해야 한다. Spec 2·4의 실제 환경 검사와 함께 수행한다.
- [설정 메뉴](features/configuration-menu.md): 자동 검사한 설정 저장·이행·복구 외에도 설치된 앱에서 이미지와 문구 편집, 오류 안내 등 실제 UI를 확인한다. 설정·이미지 사본의 제거 시 보존은 Spec 2·3과 함께 확인한다.
- [Spec 3](features/security-review-and-hardening.md)의 과거 시점 서술도 현재 구현과 대조한다. 특히 과거 ‘설치 미구현’ 기록에 주의한다. 과거 검사 결과는 새 결과와 시점을 구분한다.

## 권장 진행 순서

1. **다른 PC로 현재 작업을 옮기고 기준을 재현한다.** 미커밋·미추적 파일을 포함해 인계하고, `git status --short`, SDK와 Inno Setup을 확인한다. [테스트 안내](../CodexPet.Tests/README.md)의 기존 검사를 실행한다.
2. **Spec 2의 실제 환경 검증부터 진행한다.** 기존 훅이 있는 계정과 없는 격리 환경에서 실제 Codex, 설치 화면, 오류·복구를 확인하고 수정한다. 이미지·상태·설정 화면도 함께 살펴 Spec 3에 결과를 전달한다.
3. **Spec 1을 완성한다.** 공통 버전, 재현 가능한 빌드, 라이선스·고지와 배포 절차를 마련한다. 라이선스 선택은 권리자의 결정을 받는다. Spec 2의 변경이 패키지에 반영되는지 확인한다.
4. **Spec 3을 재점검한다.** 실제 설치 흐름과 배포 구성을 대상으로 위협·의존성·미서명 파일을 검증한다. 같은 계정의 파이프 위조·선점 위험은 0.1.0에서 수용했으며, 다른 미완료 항목은 결과와 함께 판단한다. 대책으로 코드나 구성이 바뀌면 해당하는 Spec 1·2 검사로 되돌아간다.
5. **Spec 4의 최종 확인을 진행한다.** Windows Sandbox의 설치·실행·이미지 재생과 후보 파일 해시 일치는 사용자 보고를 받았다. Sandbox의 Codex 연동은 시험하지 않았다. 라이선스 조건을 확인하고 건너뛴 시험은 미검증으로 보고하며 사용자 승인 후에만 공개한다.

## 다시 시작할 때 쓸 명령

상세 주의 사항은 [테스트 안내](../CodexPet.Tests/README.md)와 [설치 안내](features/installation-guide.md)를 따른다. 아래는 저장소 루트에서 실행한다.

```powershell
git status --short
dotnet build CodexPet.slnx -m:1 -p:UseSharedCompilation=false
dotnet run --project CodexPet.Tests --no-build
```

파이프 통합 검사는 실제 이름의 파이프와 새 진단 로그를 잠시 사용한다. 위젯을 종료하고 다른 CodexPet 훅이 실행되지 않는 상태에서 실행한다.

```powershell
dotnet run --project CodexPet.Tests --no-build -- --integration
```

설치 파일 빌드와 격리 시험에는 Inno Setup 컴파일러가 필요하다. 아래 경로는 예시이므로 다른 PC의 실제 `ISCC.exe` 경로를 지정한다. 시험용 설치는 작업 공간의 `artifacts` 아래에서 실행한다.

```powershell
.\installer\build.ps1 -InnoCompiler 'C:\path\to\ISCC.exe'
.\installer\test-isolated.ps1 -InnoCompiler 'C:\path\to\ISCC.exe' -PublishRoot 'C:\path\to\artifacts\builds\<식별자>\publish'
```

빌드 출력에 표시된 게시 폴더를 격리 시험에 지정한다. 빌드 결과는 `artifacts\setup\CodexPet-Setup-0.1.0-win-x64.exe`다. 실패한 빌드 이후 이전 파일이 남아 있을 수 있다. 이는 미서명 시험 파일이며 최종 릴리스 승인을 뜻하지 않는다. 재빌드하면 내용과 해시가 달라질 수 있으므로 공개할 파일을 확정한 뒤 해시를 기록한다. 현재 절차는 [빌드 안내](features/distribution-build-guide.md)를 따른다.
