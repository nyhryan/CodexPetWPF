# Spec 4. 0.1.0 릴리스 검증과 최종 배포 파일 준비

## 상태

**구현 및 최종 검증 진행 중.** [질문지](release-validation-and-distribution-questions.md)의 답변을 반영했다. 항상 위에 표시 및 [트레이 숨기기 기능](configuration-menu.md#설정-화면과-우클릭-메뉴)을 반영한 새 후보를 빌드하고 자동 검사를 재실행했다. 새 후보의 실제 설치·화면 시험과 .NET 배포 조건 확인은 남았다. 사용자가 이전 후보에 대해 보고한 Windows Sandbox 설치·실행·이미지 재생 결과는 새로운 파일의 시험 결과가 아니다. Sandbox에서 `dotnet` 명령은 발견되지 않았고 Codex 연동은 시험하지 않았다. 사용자는 Sandbox의 Codex 연동 및 기존 훅·다른 Windows 계정에 관한 추가 시험을 미검증으로 두고 진행하기로 했다.

이 후보를 만든 뒤 [라이선스 추가 조사](distribution-license-review.md#추가-조사와-배포-방침--2026-11-10)에서 Microsoft의 .NET Library 및 Windows SDK 조건을 따로 다루기로 정했다. 사용자의 진행 요청에 따라 오프라인 참고 사본과 라이선스 확인 화면을 포함한 빌드 `f6e3d553f1a04819968488e64b26d3a8`을 만들고 별도 시험용 설치 파일의 동의 인자·설치·제거를 격리 검사했다. 정확한 적용 약관과 동의 방식의 법적 적합성 및 실제 화면 동작은 아직 확인되지 않았다. 이전 후보의 검사 결과를 새 파일의 실제 화면 검증으로 옮기지 않는다.

**2026-11-10 사용자 확인:** 사용자가 앞서 남은 두 항목으로 안내한 설치 파일의 라이선스 화면·트레이 동작과 Microsoft 라이선스 조건을 확인했다고 보고했다. 확인 환경, 시험 파일의 해시, 개별 조작 결과와 라이선스 확인 근거는 별도로 제공되지 않았으므로 기록된 자동 검사나 외부 법률 검토의 증거로 확대하지 않는다. 이 확인은 커밋 요청과 함께 전달됐으며 푸시나 GitHub Release 공개 승인은 아니다.

## 목적과 범위

Spec 1~3의 결과를 한데 모아 Windows 11 x64의 로컬 Codex 사용자가 같은 설치 파일로 설치·사용·제거할 수 있는지 확인한다. 수정이 끝난 소스에서 Release self-contained 설치 파일을 만들고, 실제 포함 파일·고지·서명 상태와 SHA-256을 확인해 릴리스 안내를 준비한다. 실제 공개는 검증 결과와 별도 릴리스 승인 이후에 진행한다.

0.1.0의 기존 결정은 설치 파일 하나, 공개 GitHub Releases, 사용자별 고정 위치, 수동 위젯 실행, 미서명 배포다. Windows ARM64, WSL, 원격·클라우드 작업, 자동 시작과 자동 업데이트는 대상이 아니다. 여러 세션의 이벤트는 도착 순서대로 표시된다.

사용자는 설치 화면과 Codex 기본 흐름을 기존 시험에서 직접 확인했고, Sandbox에서 Codex 연동의 추가 시험은 진행하지 않기로 했다. 사용자는 검사 결과를 보고 최종 공개를 승인하며, 승인 후 에이전트가 GitHub Releases 공개 작업을 진행한다. 문의처는 공개 저장소의 GitHub Issues이며, 사용 가능 여부와 비로그인 열람 가능성은 공개 전에 확인한다. 이 결정은 지금 당장의 공개 승인이 아니다.

## 전제와 시험 환경

- 먼저 Spec 1~3의 배포를 막는 수정과 패키지 변경을 마무리한다. 변경된 부분은 관련 자동 검사와 Spec으로 돌아가 재검증한다. 실제 결과와 남은 항목을 각 결과 문서에 기록한다.
- [설정 메뉴 명세](configuration-menu.md)의 항상 위에 표시 토글을 구현한 후 켜짐·꺼짐, 메뉴의 상태 표시, 재실행 후 유지와 기존 설정 보존, 설정 창이 위젯에 가려지지 않는 동작을 검사한다. 기능이 반영된 새 설치 파일로 설치·실행과 해당 동작을 확인하고 새 SHA-256 및 릴리스 안내를 갱신한다. 기존 후보의 해시·Sandbox 결과와 새 파일의 결과를 구분한다.
- 트레이 숨기기·복원, 트레이의 설정·항상 위에 표시·종료, 설정 창이 열린 상태와 숨긴 동안의 상태 이벤트를 새 설치 파일에서 확인한다. 작업 표시줄에 위젯이 나타나지 않고 종료 시 트레이 아이콘이 사라지는지도 확인한다.
- 최종 파일 시험에는 지원 대상 Windows 11 x64와 실제 로컬 Codex를 사용한다. 사용자는 Windows Sandbox에서 설치·실행 및 이미지 설정을 시험했고 결과는 아래에 기록했다. `dotnet` 명령을 찾지 못한 관찰과 파일 해시·환경 정보의 확인 범위도 구분한다. 추가 시험 시 Windows 버전·에디션·빌드, 계정 권한, Codex 제품·버전, 셸과 경로를 확인 가능한 범위에서 기록하고 시험 파일 해시를 비교한다. 위젯 실행만으로 Codex 이벤트 연동이나 일반 사용자 권한 설치를 검증한 것으로 간주하지 않는다.
- 기존 훅과 다른 Windows 계정에 관한 추가 시험은 사용자 선택에 따라 이번에 건너뛴다. 기존 합성 설정 시험은 기록된 범위에서만 유효하며 실제 기존 훅의 실행과 다른 계정·권한 수준의 접근을 검증한 것으로 간주하지 않는다. 경로의 공백·한글·특수 문자는 가능한 환경에서 확인하고 조건별 결과를 기록한다. 한 환경에서 관찰한 결과를 다른 환경의 성공으로 추정하지 않는다.
- 실제 사용자 데이터와 다른 프로그램 훅을 변경하지 않도록 격리된 계정·VM이나 명시적으로 준비한 시험 환경과 합성 설정·이미지를 쓴다. 설정의 백업 및 복구 방법을 확인하고, 실제 데이터는 임의로 삭제하거나 기록하지 않는다. 파이프 통합 시험은 실제 이름의 파이프를 사용하고 새 진단 로그를 만들 수 있으므로 위젯과 다른 CodexPet 훅을 종료한 상태에서 실행한다.

## 최종 빌드와 파일 식별

1. 소스 커밋, 작업 트리 변경 사항, 제품 버전, Windows·SDK·Inno Setup 버전과 도구 출처를 기록한다. 변경분이 있다면 빌드에 포함된 내용을 식별 가능하게 남기고 최종 소스를 확정한다. NuGet 복원과 컴파일러 획득에 필요한 환경을 확인한다.
2. [빌드 안내](distribution-build-guide.md)의 `installer\build.ps1`을 실행해 새로운 빌드의 게시 폴더와 설치 파일을 만든다. 성공 메시지, 빌드 폴더, 각 포함 런타임 버전을 기록한다. 실패한 실행 뒤 `artifacts\setup`에 남은 이전 파일은 성공 결과가 아니다.
3. 해당 빌드의 게시 폴더로 [격리 시험](../../CodexPet.Tests/README.md)을 실행한다. 별도 시험 설치 파일의 결과는 최종 설치 파일 자체의 화면·사용자 시나리오 결과와 구분한다. 앱·훅·설치 보조 프로그램과 런타임, 버전, 설치된 `Licenses`를 확인하고 개인 `assets`, 기존 GIF, 사용자 설정·이미지와 불필요한 디버그 파일이 포함되지 않았는지 검사 범위와 함께 기록한다.
4. 최종 설치 파일의 Authenticode 서명 상태가 미서명인지 확인한다. 그 파일의 이름·크기·경로·SHA-256을 기록하고 같은 빌드의 사본 및 이후 시험에 사용한 파일의 해시를 비교한다. 해시는 신뢰할 수 있는 경로의 비교값과 파일이 일치하는지 확인하며 게시자 신원을 증명하지 않는다.
5. 직접·추이 NuGet 패키지, 포함 런타임과 Inno Setup의 실제 버전·출처, 알려진 취약점과 확인 시점을 기록한다. CodexPet MIT, XamlAnimatedGif 및 기타 실제 포함 구성의 고지, .NET 런타임 배포 조건과 Inno Setup 사용 조건을 확인한다. 필요 고지가 설치된 파일 또는 함께 제공할 문서에 있는지 확인하고 미확정 조건은 완료로 표시하지 않는다.
6. 이후 아래 시나리오와 릴리스 초안에 **동일한 SHA-256의 설치 파일**을 사용한다. 소스·포함 파일을 바꾸거나 다시 빌드하면 새 파일로 식별하고 관련 검사와 실제 파일 검증, 해시 및 안내를 다시 수행한다. 기존 시험 결과를 새 파일의 통과 근거로 옮기지 않는다.

해시 계산 예시:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath <최종_설치파일_경로>
```

6. **보안:** Spec 3의 합성 민감 표식·입력 제한·로그·회복 자동 검사를 다시 실행한다. 다른 계정과 권한·무결성 수준의 파이프 접근 시험은 이번에 건너뛰고 미검증으로 기록한다. 연속 점유의 영향, 실제 정상 이벤트 크기와 1 MiB·1초 제한의 적절성을 점검한다. 실제 입력을 조사할 때 민감한 원문은 수집하거나 기록하지 않는다. 설정·이미지·로그의 권한과 실행 파일·설정 변조 영향은 격리된 시험 데이터로 확인한다.

## 합격과 공개 판단

- 필수 시나리오에서 설치·Codex 작업·제거가 정상 동작하고, 기존 훅과 사용자 데이터의 보존·선택적 삭제가 약속대로 확인돼야 한다. 기존 훅 관련 추가 시험을 건너뛰므로 이전 격리 시험 범위 밖의 보존·동작은 이 기준을 충족한 것으로 표시하지 않는다. 실사용을 막는 문제, 재현 가능한 데이터 노출·기존 설정 손상, 필수 고지 누락은 수정하고 영향을 받는 검사를 다시 통과할 때까지 공개를 막는다.
- 사용자가 수용한 같은 계정의 파이프 위조·선점 위험은 [기록된 범위](security-review-results.md#2026-11-10-릴리스-전-재점검)에서 0.1.0의 알려진 제한으로 안내한다. 다른 사용자 접근과 가용성 시험 결과까지 수용한 결정은 아니다. 새로 발견된 문제와 미검증 항목은 영향·재현 조건·근거·담당 판단을 별도로 기록한다.
- [릴리스 안내 초안](distribution-release-draft.md)에 실제 지원·검증 환경, 공식 GitHub Releases 위치, 파일명과 최종 SHA-256, 미서명 및 Windows 경고, 설치·훅 신뢰·삭제, 로그와 GitHub Issues 문의 방법, 변경 사항 및 제한을 채운다. 공개 전 저장소·Issues·안내의 접근 가능성을 확인하고, 실제 공개 후에는 비로그인 다운로드 파일의 해시와 안내를 확인한다. 공개 전 검증과 공개 후 확인을 구분한다.
- Windows Sandbox의 기본 설치·실행 결과와 **이전** 후보 파일에 일치하는 해시를 보고받았다. 새 후보의 검증은 별도다. 사용자는 Sandbox의 Codex 연동 및 기존 훅·다른 계정 관련 추가 시험을 미검증 상태로 진행하기로 했다. 구체적인 미검증 범위는 릴리스 안내와 공개 판단에 기록한다. 차단 문제가 남으면 공개하지 않는다. [라이선스 점검](distribution-license-review.md)의 .NET 배포 조건·고지 확인은 남았다. 사용자가 결과를 확인하고 별도로 승인한 뒤 에이전트가 최종 공개 및 파일 업로드를 수행한다.
