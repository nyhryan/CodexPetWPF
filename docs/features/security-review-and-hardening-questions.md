# Spec 3. 0.1.0 보안 점검 및 개선: 결정할 질문

이 문서는 [Spec 3 초안](security-review-and-hardening.md)을 완성하기 위한 질문입니다. 각 질문에서 원하는 `[ ]`를 `[x]`로 바꾸거나 `1-A, 2-B, 3-A ...`처럼 답해 주세요. **“추천대로”**라고 답하거나 다른 의견을 직접 적어도 됩니다. 추천은 아직 확정된 정책이 아닙니다.

이미 정한 방향은 **현재 필요한 정보만 파이프로 전달**하고, 설치 파일에 SHA-256 해시 확인 방법을 제공하는 것입니다. 해시는 배포자 신원 증명이 아닙니다. 도구 이름 표시 기능을 0.1.0에 넣을지는 이 질문지에서 정하지 않습니다.

## 1. 진단에 세션 ID를 사용할까요?

세션 ID는 오류가 어느 Codex 작업에서 발생했는지 추적하는 데 도움이 되지만 작업들을 서로 연결할 수 있는 식별 정보입니다. 현재 위젯의 상태 표시는 세션을 구분하지 않습니다.

- [x] **A. 세션 ID를 파이프와 로그에서 모두 제외합니다.** 작업별 문제 추적은 어려워집니다. **추천: 현재 화면에 필요하지 않은 정보를 줄입니다.**
- [ ] B. 세션 ID를 파이프로 보내고 훅과 앱의 진단 로그에도 기록합니다. 작업별 추적은 쉽지만 식별 정보가 남습니다.
- [ ] C. 훅의 로컬 로그에만 기록하고 파이프와 앱 로그에는 보내지 않습니다. 앱 쪽 작업별 추적은 어렵습니다.
- [ ] D. 직접 정하기: ___

## 2. 화면 상태를 바꾸지 않는 이벤트는 어떻게 다룰까요?

현재 `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`은 화면을 바꾸지 않지만 훅에서 전달하고 진단 로그를 남깁니다.

- [x] **A. 이 이벤트는 위젯에 보내지 않고, 일반 로그에도 기록하지 않습니다.** 화면 동작은 유지되지만 해당 이벤트의 전달 여부를 로그로 확인할 수 없습니다. **추천**
- [ ] B. 이벤트 이름만 위젯에 보내고 진단 기록 대상으로 삼습니다. 상태는 바꾸지 않습니다.
- [ ] C. 위젯에는 보내지 않고 훅에서만 진단 기록 대상으로 삼습니다.
- [ ] D. 직접 정하기: ___

`SessionStart`의 `source: compact`는 별도입니다. 상태 전환 규칙을 유지하려면 이 이벤트와 `source`를 처리해야 합니다.
진단 기록 대상으로 선택하더라도 실제 기록 여부는 질문 3의 로그 수준을 따릅니다. 예를 들어 질문 3에서 오류만 기록하도록 선택하면 정상 이벤트는 기록하지 않습니다.

## 3. 진단 로그를 언제 남길까요?

- [x] **A. 기본적으로 오류·실패만 기록합니다.** 정상 이벤트 흐름의 상세 추적은 어렵습니다. **추천: 평소 기록을 줄입니다.**
- [ ] B. 오류와 정상 이벤트 이름을 모두 기록합니다. 문제 추적이 쉽지만 활동 기록이 더 많이 남습니다.
- [ ] C. 기본적으로 기록하지 않고 사용자가 진단을 켰을 때만 기록합니다. 켜는 방법과 종료 방법을 함께 만들어야 합니다.
- [ ] D. 직접 정하기: ___

어떤 선택을 하더라도 원본 JSON과 `prompt`, `tool_input`, `tool_response`는 로그에 남기지 않도록 검사합니다. 세션 ID는 질문 1의 선택을 따릅니다.

## 4. 로그를 얼마나 보관하고 기존 로그는 어떻게 할까요?

각 묶음에서 하나씩 선택해 주세요. 삭제는 CodexPet 로그에만 적용하며 사용자 이미지나 설정에는 적용하지 않습니다.

**새로 생성되는 로그**

- [x] **A. 크기를 제한해 오래된 로그부터 자동 정리합니다.** 구체적인 크기와 보관 파일 수는 구현 시 정하고 안내합니다. **추천**
- [ ] B. 일정 기간이 지난 로그를 자동 정리합니다. 기간: ___일
- [ ] C. 자동 정리하지 않고 위치와 수동 삭제 방법을 안내합니다. 로그가 계속 커질 수 있습니다.
- [ ] D. 직접 정하기: ___

**새 정책 적용 전에 이미 생긴 로그**

- [x] **E. 자동 삭제하지 않고 위치와 수동 삭제 방법을 안내합니다.** 이전 기록은 사용자가 지우기 전까지 남습니다. **추천: 기존 파일을 임의로 지우지 않습니다.**
- [ ] F. 새 정책 적용 시 기존 CodexPet 로그도 정리합니다. 정확한 대상과 적용 시점을 안내해야 합니다.
- [ ] G. 직접 정하기: ___

## 5. 같은 계정의 다른 프로세스는 어디까지 방어할까요?

현재 파이프는 `CurrentUserOnly`를 사용하지만, 이것만으로 같은 Windows 계정의 다른 프로세스가 진짜 훅이나 위젯인지 확인하지는 않습니다. 같은 계정의 프로그램이 이벤트를 위조하거나 위젯보다 먼저 가짜 서버를 열 수 있는 조건을 점검해야 합니다.

- [x] **A. 실제 가능한 조건과 영향을 검증하고, 0.1.0에 필요한 대응을 결정합니다.** 추가 인증이 필요하지 않다고 판단하면 근거와 남은 위험을 공개합니다. **추천: 검증 결과에 맞춰 범위를 정합니다.**
- [ ] B. 같은 계정의 다른 프로세스도 구분할 수 있는 상대방 인증을 0.1.0의 필수 목표로 삼습니다. 가능한 방식과 한계, 설치·운영 복잡도 및 실패 시 동작을 설계·검증해야 합니다.
- [ ] C. 같은 계정의 다른 프로세스는 신뢰 범위에 둡니다. 해당 위조·가짜 서버 위험과 그 영향을 릴리스 안내에 명시합니다.
- [ ] D. 직접 정하기: ___

어떤 선택이든 입력 크기·시간 제한과 잘못된 입력 후 정상 처리 여부는 점검합니다. 구체적인 제한값은 정상 Codex 이벤트 크기와 사용자 경험을 확인해 정합니다.

## 6. 0.1.0 배포물에 코드 서명을 적용할까요?

코드 서명은 배포자 확인과 파일의 서명 검증에 쓰입니다. 인증서 확보·관리와 비용, 실제 서명 대상 및 검증 절차를 확인해야 합니다. 서명되지 않은 실행 파일에는 Windows 경고가 표시될 수 있습니다.

- [x] **A. 0.1.0은 우선 서명 없이 준비합니다.** 서명되지 않았음을 밝히고 공식 다운로드 위치, SHA-256 해시와 확인 방법, 발생 가능한 경고를 안내합니다. 배포자 신원은 해시만으로 증명되지 않습니다. **추천: 우선 배포 절차를 단순하게 합니다.**
- [ ] B. 0.1.0 공개 전에 코드 서명을 적용합니다. 인증서와 서명 대상·검증 절차를 먼저 확정합니다.
- [ ] C. 인증서 비용과 발급 가능성을 조사한 뒤 결정합니다. 결정 전에는 서명 정책 관련 완료 기준을 통과한 것으로 표시하지 않습니다.
- [ ] D. 직접 정하기: ___

## 7. 발견한 문제는 어떤 기준으로 배포를 판단할까요?

- [x] **A. 배포를 막는 문제를 수정·재검증하고 나머지는 영향과 이유를 기록해 릴리스 때 판단합니다.** 보안 점검에서 차단 기준과 판단자를 명시합니다. **추천**
- [ ] B. 발견된 보안 문제를 모두 수정하고 재검증한 뒤에만 배포합니다. 경미한 문제도 공개 일정에 영향을 줄 수 있습니다.
- [ ] C. 직접 정하기: ___

## 답변 후 확정할 내용

- 전송 및 진단의 허용 필드, 상태에 영향을 주지 않는 이벤트 처리와 기존 로그 처리.
- 로그 기록 수준·보관 방식, 파이프 상대방에 대한 신뢰 범위와 확인된 위험의 대응.
- 서명 적용 대상 및 검증 방법, 미해결 문제의 배포 차단·수용 기준.
- Spec 2의 설치·삭제 설계와 Spec 1·4의 배포물 및 릴리스 검증에 전달할 요구사항.
