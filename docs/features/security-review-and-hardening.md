# Spec 3. 0.1.0 보안 점검 및 개선

## 상태

**답변 반영 — 일부 구현 및 점검 진행 중.** [질문지](security-review-and-hardening-questions.md)의 선택을 반영했다. 이 명세 자체는 보안 점검 완료나 릴리스 승인을 뜻하지 않는다. 0.1.0은 우선 코드 서명 없이 준비한다.

구현 이후의 검증 결과와 남은 항목은 [보안 점검 결과](security-review-results.md)에 별도로 기록한다. 설치 및 최종 배포물 검증은 아직 완료되지 않았다.

## 목적과 범위

0.1.0 공개 전에 Codex 이벤트가 위젯으로 전달되고 설치·실행·삭제되는 과정에서 실제로 발생할 수 있는 문제를 점검한다. 불필요한 이벤트 정보의 전송을 줄이고, 발견 사항을 재현·수정·재검증해 남은 제한을 릴리스 판단에 전달한다.

- 대상은 앱과 훅 실행기, named pipe, 설정·이미지·로그, 설치 및 전역 훅 등록·삭제, 의존성과 배포물이다. [Spec 1](windows-distribution-package.md)의 Windows 11 x64 로컬 Codex 범위를 따른다.
- 설치·삭제와 전역 훅의 사용자 흐름은 Spec 2에서 정한다. 이 Spec은 설계와 구현에 적용할 보안 요구사항을 정하고 검증한다. 설치 구현이 없으면 해당 검증을 완료한 것으로 표시하지 않는다.
- 점검과 수정은 설치 설계 단계부터 시작하고 설치 구현 및 최종 배포물이 준비되면 다시 확인한다. 실제 공개 여부는 Spec 4에서 결정한다.
- 권한 상승, 다른 사용자 계정, 같은 계정의 다른 프로세스, 잘못된 입력과 실행 파일·설정의 변조 등 검토 대상과 가정을 기록한다. 같은 계정의 다른 프로세스에 대해서는 실제 가능한 조건과 영향을 검증한 뒤 0.1.0에 필요한 대응을 결정한다.

## 현재 코드에서 확인한 흐름

아래는 Spec 3 구현 전의 코드 확인 기록이며 현재 구현 설명이 아니다. 구현 이후 결과와 실제로 확인한 범위는 [보안 점검 결과](security-review-results.md)를 따른다.

1. [프로젝트 훅 설정](../../.codex/hooks.json)이 개발용 훅 실행기를 호출한다. [훅](../../CodexPet.Hook/Program.cs)은 표준 입력 전체를 읽어 JSON으로 해석하고, 정규화한 **원본 JSON 전체**를 `CodexPet.Events` named pipe로 보낸다. 연결 제한 시간은 200ms이고 연결·전송에는 500ms 취소 제한이 있다. 실패해도 종료 코드 0을 반환한다.
2. [파이프 서버](../../CodexPet.App/PetPipeServer.cs)는 `CurrentUserOnly` 옵션으로 한 번에 연결 하나를 받아 한 줄 JSON을 읽는다. 읽기 시간 제한은 2초지만 메시지 크기 제한은 현재 코드에 없다. 이벤트를 읽지 못하거나 JSON이 잘못되면 처리 후 다음 연결을 기다린다.
3. [상태 전환 코드](../../CodexPet.App/PetState.cs)는 `hook_event_name`과 `SessionStart`의 `source`를 사용한다. [훅 입력 정보 필요도](../references/hook-input-priorities.md)는 다른 필드와 상태에 영향을 주지 않는 이벤트의 역할을 설명한다.
4. [진단 로그](../../CodexPet.Shared/DiagnosticLog.cs)는 `%LOCALAPPDATA%\CodexPet\Logs`의 `hook.log`와 `app.log`에 시각, 프로세스 ID, 메시지, 이벤트명과 세션 ID를 JSON 줄로 추가한다. 현재 코드에는 자동 보관 기간·크기 제한이 없다. 원본 `prompt`나 도구 입력·결과를 별도 필드로 기록하는 코드는 확인되지 않았지만, 기록 가능한 문자열의 내용과 다른 출력 경로도 점검해야 한다.
5. [설정 코드](../../CodexPet.App/PetSettings.cs)는 `%LOCALAPPDATA%\CodexPet\settings.json`에 사용자 문구와 이미지 경로를, `images`에 사용자가 고른 이미지의 사본을 저장한다. 사용자의 설정과 이미지에는 개인 정보가 포함될 수 있다.

`CurrentUserOnly`는 이 설정만으로 훅 실행 파일이나 파이프 상대방의 신원을 확인한다는 뜻은 아니다. 실제 접근 범위와 위조·가짜 서버의 가능성은 지원 Windows 환경에서 검증한다. 전송 필드를 줄여도 훅이 받는 표준 입력 자체나 파이프 상대방의 신원 문제는 해결되지 않는다.

## 이벤트 전송 최소화

- 훅이 입력 JSON 전체를 파이프로 재전송하는 현재 방식을 변경한다. 허용한 필드만 새 메시지로 구성하고 허용 목록 밖의 `prompt`, `tool_input`, `tool_response` 및 그 밖의 필드는 전달하지 않는다. 중첩 필드도 검사한다.
- 허용 필드는 상태 표시에 필요한 `hook_event_name`과 `SessionStart`의 `source`다. `session_id`는 파이프에 보내지 않고 훅과 앱의 로그에도 기록하지 않는다. 확정되지 않은 추가 필드를 기본 허용하지 않는다.
- `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`은 위젯에 보내지 않고 일반 로그에도 기록하지 않는다. `SessionStart`는 별도로 처리하며, `source: compact`이면 기존처럼 현재 상태를 유지한다.
- 입력이 비어 있거나 JSON이 잘못되었거나 필수 필드가 없을 때의 처리와, `SessionStart`의 `source`가 없거나 잘못된 경우의 상태 전환을 명시하고 테스트한다. 알 수 없는 이벤트로 앱이 종료되지 않아야 한다.
- 유효한 입력에서는 [상태 표시 명세](show-state-widget.md)의 상태 전환, `source: compact`, 같은 상태 이벤트에서 GIF를 다시 시작하지 않는 동작을 유지한다. 이벤트 처리 실패나 위젯 종료가 Codex 작업을 막지 않아야 한다.
- 위젯에 도구 이름을 표시하는 아이디어는 별도 화면 기능의 결정 사항이다. 채택되면 필요한 이벤트와 `tool_name`을 이 Spec의 허용 목록 및 검증에 명시적으로 추가한다.

## 파이프 및 입력 처리 점검

- 현재 사용자 외의 접근, 같은 계정에서 이벤트 위조, 앱보다 먼저 같은 이름으로 서버 생성, 연결을 점유하거나 과도한 입력을 보내는 경우를 각각 재현 가능 조건·영향·가정과 함께 점검한다. 이름이나 시간 제한만으로 상대를 인증한다고 간주하지 않는다.
- 훅의 표준 입력과 파이프 수신 양쪽의 크기·시간·메모리 사용을 점검한다. 실제 정상 이벤트를 고려해 제한과 초과 시 처리 방식을 결정하고, 초과 입력 후에도 다음 정상 이벤트를 처리하는지 확인한다. 정상 작업이 실패 때문에 중단되지 않는지도 확인한다.
- 잘못된 JSON, 긴 입력, 개행 없는 입력, 연결만 하고 보내지 않는 경우, 연속 연결 및 앱 종료를 검사한다. `CurrentUserOnly`, 연결·읽기 제한의 실제 동작과 오류 복구를 대상 환경에서 확인한다.
- 대응은 확인된 실패 조건과 지원 환경에 맞춰 결정한다. 상대방 인증의 의무화나 같은 계정의 다른 프로세스를 신뢰한다는 가정은 미리 정하지 않는다. 추가 인증을 구현하지 않거나 일부 위협을 허용한다면 판단 근거, 범위와 영향을 결과와 릴리스 안내에 명시한다.

## 로그와 사용자 데이터

- 진단 로그는 기본적으로 오류·실패만 기록한다. 정상 이벤트 흐름과 위에 열거한 상태 미변경 이벤트를 일반 로그에 남기지 않으며, 세션 ID도 기록하지 않는다. 예외나 잘못된 입력을 기록할 때도 프롬프트, 도구 입력·결과 및 원본 JSON이 들어가지 않는지 확인한다.
- 새 로그는 크기를 제한하고 오래된 로그부터 자동 정리한다. 구체적인 크기, 보관 파일 수와 동작은 구현 시 정하고 사용자에게 안내한다. 자동 정리는 CodexPet의 새 로그에만 적용하며 설정과 이미지에는 적용하지 않는다.
- 새 정책 적용 전에 생성된 기존 로그는 자동 삭제하지 않는다. 새 로그의 크기 제한·자동 정리가 기존 로그까지 삭제하지 않도록 구분해 관리하고, 기존 로그의 위치와 수동 삭제 방법을 안내한다. 기존 기록에는 세션 ID 등이 남아 있을 수 있다.
- 설정 문구, 이미지 경로 및 이미지 사본의 저장·접근·오류 처리를 확인한다. 점검이나 삭제 시험은 격리된 테스트 데이터를 사용하고 실제 사용자 설정·이미지와 다른 프로그램의 훅을 보존한다.
- 설치·제거 시 설정과 로그의 보존·삭제 사용자 흐름은 Spec 2에서 정하며, 이 Spec에서 결정한 기록 정책과 충돌하지 않게 연결한다. 로그 실패가 앱이나 Codex 작업을 중단하지 않는지도 확인한다.

## 설치·삭제와 배포물

- Spec 2의 설치 위치, 실행 파일 경로와 인용, 기존 훅 병합·삭제, 중복 등록, 읽을 수 없는 설정과 권한을 검토한다. 잘못된 경로나 기존 훅 손상 시 실패 방식과 복구 방법을 정하고, 다른 사용자·프로그램의 설정이 변경되지 않는지 검증한다.
- 앱·훅의 직접 및 추이 의존성, 게시에 포함되는 런타임과 설치 도구의 버전·출처를 기록하고 알려진 취약점을 확인한다. 확인 시점, 사용한 도구·데이터와 결과, 영향 및 조치·예외를 남긴다. 라이선스 및 고지 확인은 Spec 1과 연결한다.
- Spec 1에서 결정한 설치 파일의 SHA-256 해시와 확인 방법을 제공한다. 해시는 비교값이 신뢰할 수 있게 전달될 때 파일의 일치 여부를 확인하는 수단이며, 해시만으로 배포자 신원을 증명하지 않는다.
- 0.1.0 배포물은 우선 코드 서명 없이 준비한다. 서명되지 않았음을 밝히고 공식 다운로드 위치, SHA-256 해시와 확인 방법 및 발생 가능한 Windows 경고를 안내한다. 해시는 배포자 신원을 증명하지 않는다.

## 검증과 결과 기록

- 합성된 민감 정보 표식을 `prompt`, `tool_input`, `tool_response`, 중첩 객체 및 허용하지 않은 필드에 넣어 실제 전송 메시지와 로그를 검사한다. 허용된 필드와 값은 선택한 정책대로 전달되고 그 외의 표식은 남지 않아야 한다. 실제 개인 데이터는 테스트에 사용하지 않는다.
- 상태 전환을 포함한 정상 이벤트, 위젯 미실행·전송 실패, 잘못된 입력 및 제한 초과 후 회복을 검증한다. 전송 내용 검사와 상태 동작 검사를 모두 수행하고 기존 파이프 통합 검사도 갱신한다.
- 기존 훅 유무, 잘못된 설정, 재설치·업데이트·제거와 사용자 데이터 보존을 격리된 Windows 테스트 환경에서 확인한다. 준비된 **실제 설치 파일**에서도 보안 요구사항과 서명·해시 정책을 확인하고 Spec 4에 결과를 전달한다.
- 결과에는 검증 대상 버전·환경·시점, 범위와 미검증 항목, 재현 조건, 영향, 심각도 판단 근거, 수정 및 재검증 증거, 남은 제한과 담당 판단을 기록한다. 배포를 막는 문제는 수정·재검증하고, 나머지 문제는 영향과 이유를 기록해 릴리스 때 판단한다. 구체적인 차단 기준과 판단자는 보안 점검 과정에서 명시한다.

## 완료 기준

- [x] 같은 계정의 파이프 위조·선점 위험은 영향과 근거를 기록하고 0.1.0에서 수용하기로 사용자가 결정했다. [보안 점검 결과](security-review-results.md)의 수용 범위와 남은 별도 계정 검증을 따른다.
- [ ] `hook_event_name`과 해당 `SessionStart`의 `source`만 파이프로 전달하고, 세션 ID와 선택하지 않은 필드 및 합성 민감 정보 표식은 전송하거나 새 로그에 기록하지 않는다. 상태 미변경 이벤트도 보내지 않으며 정상 상태 전환과 실패 시 Codex 작업 지속을 검증한다.
- [ ] 새 로그는 기본적으로 오류·실패만 기록하고 정한 크기·개수에 따라 자동 정리한다. 기존 로그는 자동 삭제하지 않으며 위치와 수동 삭제 방법을 안내한다.
- [ ] 파이프 접근과 입력 제한을 대상 환경에서 점검하고, 확인된 문제의 대응 및 남는 신원·가용성 제한을 기록한다.
- [ ] 설정·이미지·로그와 설치·훅 등록·삭제의 사용자 데이터 보존 및 오류 처리를 검증한다. 설치 구현이나 최종 배포물이 없으면 관련 항목은 미완료로 남긴다.
- [ ] 의존성·배포물 점검 결과, 서명 없이 배포한다는 사실과 해시 검증 방법을 기록하고 실제 설치 파일에서 확인한다.
- [ ] 배포를 막는 문제는 수정 후 재검증하고, 남은 문제는 영향·근거·결정자를 기록해 Spec 4의 릴리스 판단에 전달한다.
